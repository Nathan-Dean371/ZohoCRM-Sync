Project Specification: Ventrata to Zoho CRM Middleware
1. Project Overview
Goal: A reliable, asynchronous middleware application that receives webhooks from Ventrata (booking creations, updates, cancellations) and pushes them to Zoho CRM in a strictly one-way sync.

Zoho Architecture: Will utilize a custom Zoho Developer Extension to deploy a "Bookings" Custom Module to the user's CRM, ensuring standard schema and unique identifiers (e.g., Ventrata_Booking_UUID for upserting).

Hosting: Railway (App service + PostgreSQL + Redis).

2. Tech Stack
Backend: Node.js, Express, TypeScript.

Database/ORM: PostgreSQL managed via Prisma.

Queue/Message Broker: Redis with BullMQ (New addition for production stability).

Authentication: JWT for local users, OAuth 2.0 for Zoho API.

3. Codebase Audit: OCTOtoCRM (What stays & What goes)
To Keep / Refactor:

src/app.ts & src/server.ts: Basic Express boilerplate and middleware (error handling, body-parser).

prisma/schema.prisma: Keep the base models for Company, User, and OAuth token storage, but remove multi-CRM complexities.

src/services/ventrata/*: Keep the webhook validation and type interfaces (src/types/ventrata.ts).

src/services/zoho/*: Keep zoho-auth.ts (OAuth token generation/refresh logic) and the base zoho-crm-service.ts API wrappers.

src/middleware/auth.ts: Keep local JWT auth for the dashboard.

To Discard:

src/services/Bitrix/* & src/services/Freshsales/*: Strip entirely.

src/routes/bitrixHandler.routes.ts & Freshsales routes: Strip entirely.

src/types/Bitrix.ts & src/types/Freshsales.ts: Strip entirely.

src/views/ (EJS files) & src/public/: If this app only requires a basic API and an onboarding screen, heavily strip down the complex EJS admin dashboards/tunnels UI. Simplify to a single "Connect Zoho & Ventrata" settings page per Company.

src/services/Tunnels/TunnelService.ts: Discard the concept of abstract "Tunnels". Hardcode the pipeline to always be Ventrata -> Zoho.

4. Database Schema Requirements (Prisma)
The database needs to handle multi-tenancy (if supporting multiple companies) and state management.

Company/Tenant Model: Stores the Ventrata API Key/Webhook Secret.

Zoho_OAuth Model: Stores access_token, refresh_token, expires_at, linked to the Company.

Webhook_Logs Model (Optional but recommended): A log of received webhook payloads and their processing status (Pending, Success, Failed) for debugging.

5. Core Workflows to Implement
A. Onboarding & Authentication Flow

User creates an account on the Railway-hosted app.

User installs the custom Zoho Extension in their CRM instance.

User completes Zoho OAuth flow in the app (saving the refresh token).

User inputs Ventrata webhook secret into the app.

B. The Webhook Pipeline (Asynchronous)

Receive: Express route POST /webhook/ventrata receives payload.

Validate: Verify the Ventrata signature using the stored Company secret.

Queue: Push the payload onto a BullMQ Redis queue and immediately return 200 OK to Ventrata.

Process (Worker):

Parse Ventrata payload (Customer details, Booking details, Products).

Check token validity, refresh Zoho access token if necessary.

Step 1: Upsert Zoho Contact (Match by Email).

Step 2: Upsert Zoho Booking (Custom Module) using the unique Ventrata_Booking_UUID. Link to the Contact ID.

Handle Failure: If Zoho API limits are hit or network fails, the job goes into a retry loop with exponential backoff. If it fails permanently, it moves to a Dead Letter Queue (DLQ).
